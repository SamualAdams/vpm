# PR 3: Domain model — threads, plays, insights, actions

## Summary
Introduce the core operating model: threads, playbooks, plays, runs, insights, recommended actions with typed schemas, action lifecycle states, and full audit trail.

## Why
The product is not just chat. It needs first-class domain records so we can track source lineage from conversation through insight to action, measure effectiveness, and support both conversational and scheduled workflows.

## Scope

### Schema (Alembic migrations)
- **threads** — conversation containers
  - `id`, `title`, `source` (enum: `conversation`, `play_run`), `created_at`, `updated_at`
- **playbooks** — named collections of plays
  - `id`, `name`, `description`, `created_at`
- **plays** — individual workflow definitions within a playbook
  - `id`, `playbook_id` (FK), `name`, `description`, `chain_name` (references the LangChain chain to execute), `ordinal`
- **runs** — execution records
  - `id`, `thread_id` (FK), `play_id` (FK, nullable for ad-hoc conversations), `status` (enum: `running`, `completed`, `failed`), `started_at`, `completed_at`
- **insights** — observations generated by runs
  - `id`, `run_id` (FK), `observation` (text), `evidence` (JSON — list of references to work items, PRs, commits), `confidence` (float 0–1), `created_at`
- **recommended_actions** — proposed changes derived from insights
  - `id`, `insight_id` (FK), `action_type` (enum, see taxonomy below), `payload` (JSON, schema depends on action_type), `status` (enum: `open`, `approved_pristine`, `approved_modified`, `dismissed`, `completed`, `failed`), `created_at`, `updated_at`
- **action_events** — audit trail for every state transition
  - `id`, `action_id` (FK), `from_status`, `to_status`, `modifier` (who/what triggered the transition), `diff` (JSON, captures modifications for `approved_modified`), `timestamp`
- **citations** — structured references from thread content to Azure DevOps entities
  - `id`, `thread_id` (FK), `entity_type` (enum: `work_item`, `pull_request`, `commit`), `entity_id` (external ID), `entity_url` (Azure DevOps URL), `context` (text snippet where cited)

### Action type taxonomy
Each action type has a defined payload schema:

| Action Type | Payload Fields |
|---|---|
| `create_work_item` | `work_item_type`, `title`, `description`, `parent_id` (optional), `assigned_to` (optional) |
| `update_work_item` | `work_item_id`, `field_changes` (JSON object of field → new value) |
| `link_pr_to_story` | `pull_request_id`, `work_item_id`, `repository` |
| `move_work_item` | `work_item_id`, `from_state`, `to_state` |
| `assign_owner` | `work_item_id`, `assignee` |
| `confirm_relationship` | `parent_id`, `child_id`, `relationship_type` (e.g., `parent-child`, `related`) |

### Service layer
- CRUD methods for all entities
- `create_thread()`, `create_run()`, `create_insight()`, `create_action()`
- `transition_action(action_id, to_status, modifier, diff=None)` — enforces valid transitions and creates audit event
- `get_thread_detail(thread_id)` — returns thread with linked runs, insights, actions
- Query methods: by thread, by run, by insight, by action status, by date range

### Playbook definition
- Playbooks and plays are stored as DB records, not files
- A playbook contains an ordered list of plays
- Each play references a `chain_name` that maps to a LangChain chain (defined in PR 4b)
- Seed data: at least one built-in playbook (e.g., "Transcript Analysis") with plays for transcript parsing and action generation

## Acceptance Criteria
- All migrations apply cleanly on top of PR 2a's schema
- Full lifecycle test passes: create thread → create run → create insight → create action → approve pristine → complete
- Modified approval path works: create action → approve modified (with diff captured) → complete
- Dismissal path works: create action → dismiss
- Invalid transitions are rejected (e.g., cannot go from `dismissed` to `approved_pristine`)
- `get_thread_detail()` returns complete lineage: thread → runs → insights → actions with events
- Action payload validation enforces the correct schema for each action type
- Citation CRUD works and citations are queryable by thread
- All service methods have tests

## Out of Scope
- Automatic scheduling of play runs
- LangChain chain implementations (PR 4b)
- Azure mutation execution (PR 4a apply flow)
- UI rendering of any of these entities
- Advanced heuristics for linking repos to stories

## Risks / Notes
- Keep the action type taxonomy extensible — use an enum but don't make it impossible to add types later
- The `evidence` field on insights is a JSON list of references, not a foreign key — this keeps it flexible for mixed evidence types
- Playbook seed data should be idempotent (safe to re-run)
- Source lineage integrity is critical — if this is broken, PR 6 (effectiveness metrics) cannot function
